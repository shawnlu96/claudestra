# ACP 适配器维护流程

ACP 宿主背后是两种适配器：Codex 用上游的 [codex-acp](https://github.com/agentclientprotocol/codex-acp)，Pi 用本仓的 `src/lib/acp/pi-adapter/`。上游 CLI 和 codex-acp 几乎每周发版，组合一换，协议就可能对不上。

本文规定一套可重复的流程，管一个「CLI × 适配器」组合从被发现、验证、上线到回退的全过程。流程分 6 张 PR 落地（PR-A ~ PR-F），按顺序合并。下面依次写：设计原则、判定等级、每张 PR 做什么和怎么验收、启用前必须满足的约束，最后是还没定的事。

现状（各入口怎么判配套、宿主怎么起适配器）见 [codex-acp.md](./codex-acp.md)。协议版本、必要能力和可选能力降级表在那份文档的「协议版本与能力」一节。

## 设计原则

1. **未验证 ≠ 已坏。**
   - 超出上游 npm 声明的配套范围，只说明这个组合没验证过。只有拿到明确失败证据的组合才判 `bad`。
   - 上游 CI 全绿只能证明类型和夹具兼容，不算我们整条链路的证据。
2. **schema 相同只够做候选。**
   - 协议 schema 与某个已验证组合完全相同，只用来筛选候选、缩小测试范围。
   - 晋级必须靠真实 CLI 加实际产物，把核心行为验证一遍。
3. **组合身份是一整组。**
   - 组合 = 运行时 + CLI 版本（含二进制 sha）+ 平台 + 适配器产物或源码树指纹 + 契约版本。
   - 证据绑定这一整组。版本号、`pi-adapter` 这类别名都不能单独当身份。
4. **过渡放行名单只收精确组合。**
   - 只收有观察证据的精确组合，和正常晋级分开，名单有到期日。
   - 回放（replay）只算回放证据，不算 `verified`。
5. **质量门不开整目录豁免。**
   - 上游原样导入的文件，逐个列进 guard 配置的例外范围，按防腐规则留 `raised[]`，并在提交说明里写明。
   - 本地补丁和新增代码照常过规则。代码审查时只放行明确列出、并核对过来源指纹的文件，不能给整个 `adapters/` 目录永久豁免。
   - 适配器包的检查（typecheck、上游单测、可复现构建）必须进本地 `bun run check`，不能只在 CI 里跑。
6. **构建清单单独管。**
   - 构建依赖单独放一份清单：只含打包工具，加上要打进产物的运行时依赖；本来就 external 的 CLI 不放进去。
   - 保留 optional 依赖（打包工具的平台二进制在里面），装完校验平台包的确切版本。
7. **可复现要逐字节。**
   - 固定源码树、锁文件、Node / npm / 打包工具版本和构建配置，在两个独立的干净目录分别重建，逐字节比对。产物摘要绑定行为测试。
   - 首次导入时和 npm 发布物逐字节比对，这一步只用来核对来源。
8. **实测不碰共享凭据。**
   - 自动化实测只接受专用 API key 或可控的测试 provider，拒绝 OAuth 凭据：复制出来的 OAuth 文件虽然是新 inode，refresh token 仍是共享的。
   - 每次运行新建目录，进程按环境变量白名单启动，显式给一个假的 bridge 地址，关掉 Pi 的外部扩展、技能和 MCP 发现，日志和夹具脱敏。
   - 路径逐级 realpath 都要落在根目录下；auth 文件必须是 0600 的普通文件；文件身份按 dev+ino 比较。
   - 同一个系统用户下，这些只能防误连、防状态污染，不能宣称是安全隔离。要强隔离，得用独立用户或容器。
9. **起适配器前的检查要能拒。**
   - 检查显式返回「允许 / 拒绝」，不靠抛异常：现在的 `beforeSpawn` 会吞掉 reject、照常启动。
   - 拒绝时宿主停止重试，当前回合和排队消息按失败收尾，并出卡。首次启动和退避重起都要测，断言拒绝后 spawn 次数为 0。
   - 宿主不直接写 registry，状态更新经 manager，并带 session / 代际条件。
10. **回退只用本地保留的组合。**
    - 升级失败不靠 `npm install -g` 装回旧版：那会影响整机，还可能下载失败。
    - CLI 装进不可变、按版本分开的路径，每个运行时保留完整组合，切换是原子的；回退就是切回本地保留的那一套。
11. **核心链路用可控 provider 驱动。**
    - 用可控的测试 provider 驱动真实 CLI。Codex 的 `model_providers` 支持自定义 base_url：本地起一个假的 Responses 服务，按剧本出文本、工具调用、错误和压缩。结果确定，不依赖模型的随机性，也不用人登录。
    - 真模型只做小规模的补充证据。
    - 权限场景显式设成会触发 permission 的模式（full-access 下不会弹）。
    - 证据按实际输入的组合判定，不是「文件存在就算数」。

## 判定等级

| 等级 | 含义 | 入口策略 |
|------|------|----------|
| `verified` | 这一精确组合，真实 CLI + 实际产物的核心行为验证全部通过 | 放行 |
| `transitional` | 过渡名单里有观察证据的精确组合，带到期日 | 放行；doctor 显示黄色，到期前补成 verified |
| `candidate` | 协议 schema 和某个 verified 组合完全相同，或上游声明了范围但我们还没验证 | 不放行，自动排进快速验证，通过就晋级 |
| `unverified` | 没有任何记录 | 同 candidate：自动排进快速验证，不让用户无限期等上游发版 |
| `bad` | 有明确的失败证据，附报告和修复任务号 | 拒起，走现有的 tmux 暂退路径（线程保留） |

「拒起」要等 PR-E 的运行守卫到位后，和 PR-D 的统一入口策略一起启用。那时 PR-C 的验证通道已经能在本机或 CI 里几十分钟内给出结论，不会出现「先收紧、出路最后才补」的空窗。

## 路线：6 张 PR

### PR-A 协议与契约基架

- **协议常量与检查**：`src/lib/acp/protocol.ts` 提供 `ACP_PROTOCOL_VERSION` 和 `checkInitialize()`。
  - 宿主、Pi 适配器、stub 共用这个常量。
  - `protocolVersion` 不是 1 或缺失，判不兼容；接回已有线程要 `resume` 或 `loadSession` 至少一个；fork 只在 fork 时要求。
  - `agentInfo` 记进会话。
- **不兼容怎么失败**：复用现有的启动失败通路，不新增失败类型（细节见 codex-acp.md「协议版本与能力」）。
  - 宿主出一张写明原因的卡，不标就绪，不再重起适配器。
  - manager 等就绪超时后走 `recoverFailedAcpLaunch`。
- **可选能力降级表**：steering、cancelReturnsQueue、compaction_update、AIR sessionFailure、terminal_output_delta、`promptCapabilities.image`，各自缺失时的行为。
  - 文档一份（codex-acp.md）。
  - 表驱动测试一份（`tests/acp-protocol.test.ts`），对真的宿主代码断言。
- **共享契约套件** `tests/acp-contract/`：场景按驱动参数化，现有 stub 和 Pi 回放两个驱动；Codex 回放驱动留给 PR-C，照 `ContractDriver` 接口实现。
- **stub 配置项**：stub 的 `STUB_INITIALIZE` 能改写 initialize 回包，用来测不兼容和能力缺失。
- **验收**：
  - 回 protocolVersion 2 或不回 → 拒起并出卡；`resume` 与 `loadSession` 都没有 → 拒起；可选能力缺失 → 按表降级。
  - 回 1 的现有适配器行为不变；不改生产适配器的选择和 argv。

### PR-B 源码接管、干净构建、独立质量门

- **导入**：`git subtree --squash` 导入上游正式版。
  - 附 `PROVENANCE.json`：仓库、tag、commit、许可证、版权方、本地补丁清单。
  - 保留 LICENSE，改过的文件按 Apache-2.0 §4(b) 加修改声明。
- **质量门**：
  - 上游原样的文件列进 guard 的例外范围（原则 5）。
  - `bun run check` 增加一步 `adapter:check`：typecheck、上游单测（不含 e2e）、两目录可复现构建并比对字节。CI 里也跑这一步。
- **构建清单**：独立的 package.json 和锁文件（原则 6），固定 Node / npm 版本。
- **首次导入的来源核对**：从源码构建出的产物和 npm 发布物逐字节相同；如果不同，查出原因并固定下来。
- **产物存放**：
  - 产物落进内容寻址目录 `acp/artifacts/<sha256>.mjs`，放进去后只读。
  - 宿主启动时用的就是指纹对应的那份。旧的 `codex-acp-<版本>/` 原样保留。
- 根目录 `bunfig.toml` 加 `[test] root = "tests"`，免得根目录的 `bun test` 扫到上游的测试文件。
- **验收**：只导入、构建、存放候选产物，**不替换生产适配器**（约束 1）。

### PR-C 真实组合验证（可控 provider 为主）

- `scripts/acp-compat-live.ts`：每次运行新建隔离根目录，环境变量白名单，假 bridge 只绑 127.0.0.1，宿主在进程内跑；路径和凭据检查按原则 8。
- **可控 provider**：Codex 指向本地假 Responses 服务；Pi 用它支持的 OpenAI 兼容 provider 指过去。按剧本覆盖：
  1. 文字消息加 reply；
  2. 图片附件；
  3. 工具调用的流式输出；
  4. 忙时插话（injected）加取消（cancelled，线程回到 idle）；
  5. 恢复线程：杀掉适配器，用 resume 接回，问上一轮留下的暗号；另做一次跨版本恢复，作为回退的依据；
  6. 压缩（compaction completed，出压缩边界）；
  7. 失败与权限收尾：结构化失败卡；权限请求超时回 cancelled；凭据缺失出登录卡。
- **Codex 回放驱动**：把 app-server 的 stdio 录成夹具（脱敏），接进 PR-A 的契约套件，CI 里离线跑。
- **证据 JSON 绑定整组身份**：harness 的 git sha、CLI 版本和二进制 sha、平台、适配器产物 sha、schema 哈希、契约版本、initialize 回包快照、每个场景的结果。
- 真模型小规模实测作为补充证据（凭据与额度定了才跑）。
- 规则写死并用测试锁住：只过 stub 或 replay 不能晋级成 `verified`。

### PR-D 精确兼容记录 + 统一入口策略

- **兼容记录**：`src/lib/acp/compat.json` 加 `compat.ts`，按判定等级判。记录引用的证据文件必须存在，身份要和证据里写的一致（用测试校验）。
- **替换各入口**：readiness、install、更新提示、网页更新端点、doctor、宿主起适配器前的版本对账、切 transport 前的检查，全部改用这一处判定。Pi 一起纳入。
- **candidate / unverified**：自动排进 PR-C 的快速验证，验证期间按判定等级处理。
- **过渡名单**：从实际启动记录生成，PR 里列出对照表；证实不了的组合走 PR-C 实测（约束 2）。
- **验收**：新的拒起策略**只做影子判定**，积累证据、发告警，不实际拦截（约束 1）。

### PR-E 完整组合切换、运行守卫、回退

- **不可变的 CLI 版本路径**：`npm --prefix` 装到状态目录下按版本分开的路径，每个运行时至少保留「当前 + 上一套」完整组合（CLI + 适配器产物）。宿主的 `CODEX_PATH` 指向组合路径，不再指向会被 `npm -g` 原地替换的全局文件。
- **运行守卫**：`beforeSpawn` 返回 `{allow} | {deny, reason}`，行为按原则 9。
- **升级**：先验证新组合，再原子切换；失败就切回上一套本地组合，不联网。
- 跨版本恢复线程的结论以 PR-C 场景 5 的证据为准。
- **验收**：启用后，每次实际 spawn 用的都是判定过的那一套组合（约束 1）。

### PR-F 持续检测与维护 PR

- **每日检测**：
  1. 查 npm latest，装进临时目录；
  2. 生成 schema 并 diff；
  3. typecheck、上游单测、契约测试；
  4. 跑 PR-C 的可控 provider 验证；
  5. 按结果开 PR（加记录或适配器补丁）；失败就开 issue 或修复任务，附 diff 和失败用例。
- **本机 launcher 只做轻量对账**：本机组合不在记录里，或等级是 `bad`，就建一条 ledger 事项（去重）并通知一次。

## 启用前必须满足的四条约束

1. **分阶段启用，不留空窗。**
   - PR-B 只导入源码、构建并存放候选产物，不替换生产适配器。
   - PR-D 做统一判定、积累证据、发告警，新的拒起策略只做影子判定，不实际拦截。等 PR-E 的不可变完整组合、`beforeSpawn` 守卫和切换事务到位后，再一起启用。
   - 原因：宿主进程启动时就固定了适配器 argv（`src/acp-host.ts`），`AcpHost.startAdapter` 又会吞掉检查异常、照常启动。单独上 PR-D，会出现「入口已经拒绝、存量重起却绕过检查」的状态。
   - 验收：停在 B 或 D 的版本时，旧组合照常运行，生产 argv 和适配器选择都不变；启用 E 后，每次实际 spawn 用的都是判定过的那一套组合。
2. **过渡名单不能拿旧运行记录和磁盘上当前的产物拼凑。**
   - 原因：运行版本记录（`codex-version.ts`）只记版本和时间；宿主启动之后，全局指针可能已经切换。
   - 做法：迁移时取实际启动路径、完整组合指纹，以及和 session / 代际的关联。证实不了的组合走 PR-C 实测。
   - 验收：宿主用 A 启动后把全局指针切到 B，过渡记录不得把 A 的运行观察登记到 B 名下。
3. **「当前 + 上一套」是最少保留量，不是上限。**
   - 仍被存活宿主引用的更旧组合必须保留，退避重起时要用。CLI、Codex 产物、Pi 对应的源码快照或产物，都随完整组合一起固定。
   - 回收前要确认没有存活宿主、在途切换或实测还在引用它，安全释放后才删。
   - 验收：A 宿主在线时连续切到 B、再切到 C，然后让 A 的适配器退出，A 能按原指纹重起。
4. **恢复和回退测试要防假阳性。**
   - 假 provider 不能无条件吐出暗号：要断言恢复请求里带着正确的前序对话和工具结果，并加一个错误 session 的反例。
   - 跨版本回退要测完整的「旧 → 新 → 旧」：新版要真正写入对话、工具和压缩状态，再切回旧版继续工作。只测「新版能打开旧线程」证明不了能回退。
   - 新版写出了旧版读不了的状态时，切回旧二进制不算回退成功：此时保留新组合，明确按失败收尾，不能报告「升级已恢复」。

## 待定的决定

- **源码放哪。** 二选一：
  - 本仓受控子包：宿主、记录、契约测试和适配器补丁在同一张 PR 里一起审，和 Pi 适配器的流程统一。代价是导入上千个文件，guard 例外范围、定时 workflow 和写权限都要仓库维护者同意，本仓的 check 也会变重。
  - 独立仓：工具链和上游一致，CI、secrets 和定时任务自己控制，不用在本仓开 guard 例外。代价是跨仓协作，适配器和宿主的改动要分两张 PR；本仓按指纹拉产物，还要一个分发渠道；Pi 适配器留在本仓，两套流程要靠同一份兼容记录统一。
- **实测凭据和额度。**
  - 可控 provider 不需要凭据，PR-C 主体照做。
  - 真模型补充实测要一个专用 API key（建议设预算上限），Pi 也要一家 provider 的 key。也可以先不做真模型实测。
- **要不要强隔离。** 同一系统用户下只能防误连、防状态污染；要强隔离，就开一个独立的系统用户，或用容器跑实测。
- **自动化写权限。** 每日检测放在哪个仓库的 Actions、谁授予开 PR 的权限，取决于源码放哪；本机 launcher 部分不需要额外权限。

其余事项按上面的默认做法处理，不再单独拿出来问：命名（例如 `2.1.1-cs.1`）、工程拆分、许可证留痕、只按需挑上游 PR。
