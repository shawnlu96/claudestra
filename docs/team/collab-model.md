# 协作模型：任务拆成固定步骤，每一步谁都能接（设计稿）

> 状态：定稿候选。owner 已看过；Alex（review 5348249875）、He（review 5348424868）的意见已并入。关联：[编排班子](./orchestration-team.md)、[跨实例委托](./peer-delegation.md)、台账（`src/lib/ledger-*.ts`）。

## 为什么写这份

09-29 这一天，审查、修复分别派给了本机执行者、He、Alex，还差点派给 Codex。每一步派给谁、任务单怎么写、结果怎么回来，都是 PM 在对话里当场决定、手写消息。规则只存在 PM 的脑子里，系统里没有，结果是：

- owner 看着乱，换一个 PM 就做不出同样的事；
- 同一个意图要反复解释，比如「谁查出来谁修」「安全类换个模型审」；
- 别的实例在我们这里只是几个具体的 agent，没法说「这一步交给 Alex 那边，用他们的 Codex」。

这份稿子把协作收成三个概念（流程、目录、规则）和一条通道。今天所有的临场判断，都应该落到其中某一块上。

## 1. 流程：每类任务是一条固定的步骤线

步骤是固定的：每一步的输入、产出、验收都写死。变的只有「这一步由谁来做」。代码类任务的步骤线：

| 步骤 | 输入 | 产出 | 验收 | 台账阶段 |
|---|---|---|---|---|
| 复述 | 规格卡 | 一段复述 | PM 放行 | restate |
| 写 | 规格卡 | 分支、head、PR | `bun run check` 全绿 | build |
| 初审 | head | 结论和 P0/P1/P2 | 结论针对这个 head | review |
| 修 | 审查意见 | 新 head | 同「写」 | fix |
| 终审（对抗式） | head | 结论 | 在真实环境里实打 | review |
| 看界面（有界面改动才有） | 前后对比截图（写界面的人必交） | owner 点头 | — | 待你处理 |
| 合并部署 | 通过审查的 head | 合并提交 | CI 通过、部署完成 | merge / live |
| 核对 | 合并提交 | 检查单 | `ledger verify` | verified |

调查类、运维类任务的步骤线更短，后面再补。

## 2. 目录：谁能接步骤

目录里每一项写清楚：名字、在哪台机器（本机或某个 peer）、种类（Claude / Codex / Pi / 人）、能接哪些步骤、额度（剩余多少、几点重置）、边界（能碰什么）。

- **本机**：PM、调度助理、执行者、本机 Codex、owner。
- **别的实例**：一个实例在目录里算一项，也就是一个团队，不列出它具体有哪些 agent，也不要求对方和我们同构（对方不一定有编排班子）。对方只需要提供一个固定的**入口**，比如 Alex 那边的 `agent-outer-codex@Sekai`。交过去的是「一个步骤」，入口收单后由他们自己往下分。要换模型，就在任务单上写「这一步请用非 Claude 模型」。
- **额度**：本机的读 `quota-state.json`。peer 只报三档：能接 / 忙 / 不接（Sekai 方 owner 已定），不报百分比和重置时间；不报就当未知。

## 3. 规则：谁来做是参数，按规则给建议

硬规则，owner 定一次，系统强制执行：

1. 审的人不能是写的人。一次修改的作者，不审自己改的那一段。
2. 安全类改动的终审，模型种类必须和作者不同。
3. 合并、部署、核对，只由仓库所在实例的 PM 来做。

软规则，只用来排优先顺序：

4. 额度快作废（快重置了还剩很多）的优先。peer 只能按「能接 / 忙 / 不接」三档排。
5. 谁查出问题谁去修，再由另一个人审。
6. 需要特定环境的步骤，给有那个环境的人，比如窄终端、走中继、真机。

PM 建卡时，按目录和规则给整条步骤线生成建议分工，显示在卡上。owner 点一下就能换掉某一步的执行者。

跨实例时，硬规则 1、2 只能靠对方声明：peer 只认证到实例这一层，用的什么模型是对方自报的。卡上要标清楚，哪些是系统真校验过的（比如本机的作者和审查人不是同一个），哪些是凭对方声明（比如对方说用的是 Codex）。

## 4. 通道：派单和回报只走一条路

- **派单**：某一步选定执行者后，系统按步骤模板生成标准任务单（复用 `ledger review-pack` / `dispatch` 的生成器）。本机的执行者走 `send_to_agent`；别的实例走跨实例委托，发到对方的入口，消息首行写 `[协作 <任务号>/<步骤>]`。发往 peer 的单子在生成器里先脱敏（密钥、内网地址、个人信息）。PM 不再手写任务单。
- **回报**：结果一律写回台账里对应的那一步。本机用 `ledger`，peer 用 `peer-ledger`。
- **唤醒，双向**：某一步有了结论（交付、审查结论、卡住），系统自动通知这张卡当前的接手人；接手人在别的实例上，就发给对方的入口。反过来，peer 写卡之后，系统也要唤醒我们这边的接手人，不靠谁再手写一句。消息只用来商量事情，不用来记账。

## 落地约束（接活方的意见）

**接受按任务，不按步骤。** 接活方每接一件新委托都要先问自家 owner。owner 同意的是「这张卡上派给我们的步骤」，之后同一张卡的修复轮、复核返工照做，不再逐步问。

- 卡上记一条接受事件（`accept`，带接方 owner 点按钮的时间）。派单生成器看到已接受，就发步骤单；没接受，就发新委托，走「先问 owner」的流程。
- 两种消息的首行分开：新委托写 `[协作 Txx]`，已接任务的步骤单写 `[协作 Txx/步骤]`。peer 消息的注入头只对前一种要求先问 owner，否则每次唤醒都会让对方 owner 被刷屏。

**目录项要记并发。** 比如 He 那边的入口是单个 agent，并发 = 1，同时派去的几步会排队。「忙」要把这一点算进去。对外可以合成一档，内部要分清是「额度紧」还是「手上有活」。

**权限检查细到步骤。** 现在 `peer-ledger` 看的是整张卡的 `delegate` / `reviewer`。步骤化以后，要改成判断「这一步的执行者是不是这个 peer」，否则 A 实例能推 B 实例负责的那一步。

**「作者」按步骤记。** 硬规则 1 里的作者，定义成「写或修那一步的执行者，加上它交付的 head 区间」。一张卡可能是 A 写、B 修、C 审，只看提交人会乱。

**唤醒要防来回刷和重复：**

- 只有改变状态的事件才唤醒（交付、审查结论、卡住），note 不唤醒；
- 只唤醒当前这一步的执行者；
- 按事件序号去重，断线重连或重放都不会唤醒两次。

**任务单只写步骤契约。** 只写输入、产出、验收，不夹带额外指令，接方把它当数据看。脱敏放在生成器里；生成器的输出要能被单测逐字校验。

**「看界面」谁拍谁点。** 截图由写界面的一方在自己机器上拍，点头的是仓库所在实例的 owner。

## 现在有什么、缺什么（按依赖顺序）

| # | 要做的 | 现在有什么 | 缺什么 |
|---|---|---|---|
| 1 | 每一步都能单独派人 | 一张卡只有一个执行者；审查人是塞在 `extra.reviewer` 里的 | 卡上按步骤记录谁做、结果如何；`peer-ledger` 的白名单跟着扩到步骤 |
| 2 | 统一派单 | `review-pack` / `dispatch` 能生成审查单，但只发给本机审查员 | 各步骤的模板；按执行者在哪台机器选通道 |
| 3 | 有结论就唤醒接手人（双向） | 编排班子的事件路由会通知本机接手人 | peer 写卡唤醒我们；我们写卡唤醒对方入口；覆盖终审、看界面 |
| 4 | 目录和分工建议 | 编排班子只有 PM 名单；peer 在线探测只有 agent 列表 | 目录项的模型、额度、能接的步骤；建卡时给出建议 |
| 5 | 团队对团队 | 跨实例委托协议、`peer-ledger` | 目录里记对方的入口；任务单上的「换模型」要求；卡上区分真校验和凭声明 |
