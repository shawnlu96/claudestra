# 远端审查报文的仓库与提交身份

自动认卡使用 `owner/repo + PR 号`，只在该 peer 的 handoff 项目内唯一匹配；仓库比较不区分大小写。结论生效要求报文携带的完整 40 位小写 head SHA 与卡当前 head（merge 阶段也包括 handoff 正在跟随的 head）精确相同。前 12 位相同不算匹配。

新报文保留结论、报告编号、下一步、回复地址及报告正文的语法，仅把 `head：` 改为完整 SHA，并在回复地址后、分隔线前增加 `仓库：owner/repo`。原发和补发使用同一身份；补发保留该仓库行及原审查的完整 head。正文仍然是外部数据。

inbox 文件名及报告文件名使用规范化的 repo、PR 号与完整 head 的 SHA-256 摘要；ledger 去重键包含三者以及卡号、报告编号。相同身份和轮次重复投递只入账一次，仓库名大小写变化不产生第二份。相同 repo+PR 的另一完整 head 可先入账为 `matched:false`，卡真正达到该完整 head 后只生效一次。

## 兼容与升级顺序

1. **先升级接收方**：bridge 与 manager 都识别新格式；缺 repo 或缺完整 SHA 的旧报文直接走普通 PM 投递。不 stash、不自动认卡、不用 202 截走，原发、补发及重复投递均如此。混跑期间 PM 能看到旧报文并人工处理。
2. **再升级发送方（仓库方实例）**：原发、失败重试和 PM 显式补发统一从 PR URL 取 owner/repo，发送完整 head。身份不全时拒发并保留现有 PM 告警路径。
3. 接收方升级前已经落盘的旧 inbox 文件仍会被扫描；manager 重新解析并拒绝自动入账，调度器将其移到 `failed/`，通知 PM 原文路径。直接伪造旧 inbox 也无法绕过重新校验。旧 ledger 事件保留作历史数据，缺少新身份的事件不会按短 head 延迟生效或进入当前结论查找。

渲染函数允许省略 repo，仅用于复现旧格式和兼容测试；生产审查发送路径必须提供 repo。带 repo 的 P1 补发如果仍缺少轮次上限标记，沿用已有的模糊结论规则：普通投给 PM、仅留存记录，不触发自动修复。

通知失败退避只保留本轮仍应重试的 seq：通知被其他进程确认或项目移出 handoff 配置后清掉残留；全部项目移出时清空。每个 ledger 的失败缓存最多 1000 项，超限时淘汰最早的失败项；淘汰只让该项可以提前重试，不影响未送通知的持久记录。
