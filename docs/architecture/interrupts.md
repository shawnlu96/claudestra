# Interrupts: preemption, stop words, cut records, resume hints

What happens when a human message or a stop button interrupts an agent mid-turn, and how the agent is told what was cut. Code: `src/bridge/preempt.ts` (entry points), `src/lib/interrupt-gate.ts` + `src/bridge/interrupt-gate.ts` (the only place keys are sent), `src/lib/turn-cuts.ts` + `src/bridge/turn-cuts.ts` (cut records), `src/lib/side-effects.ts`, `src/lib/stop-words.ts`, `src/lib/codex-tui-submit.ts`, `src/lib/esc-guard.ts`, Pi: `src/pi/abort-control.ts` + `src/bridge/pi-abort.ts`. Tests: `tests/interrupt-gate.test.ts`, `turn-cuts.test.ts`, `turn-cuts-book.test.ts`, `turn-state.test.ts`, `side-effects.test.ts`, `stop-words.test.ts`, `codex-tui-submit.test.ts`, `esc-guard.test.ts`, `pi-abort-control.test.ts`, `program-input.test.ts`, `held-flush.test.ts`.

## Entry points

|---|---|---|

Claude Code and Codex preempt; Pi does not (its extension steers the message into the running turn). |
| Stop word (same path) | `preemptForHuman` with `stop` | **Owner only** (`ownerStopOf` → `isOwnerSource`): from anyone else (a non-owner API token) "停" is an ordinary message, and their messages don't release the owner's stop either. Always records a stop-class cut (no resume hint, Autopilot holds), even when nothing was running; the headline says truthfully whether it interrupted. |
| Stop button, `/interrupt`, `POST /api/v1/agents/:name/interrupt` | `manualInterrupt` | Sends the runtime's key unconditionally (Codex only when busy), marks the turn done. Discord inbound used to preempt a second time before `deliver()`; that duplicate call is gone, and every human message goes through the one gate.

## Stop words (`lib/stop-words.ts`)

A message is a stop only if, after NFKC + lower-casing and dropping punctuation / whitespace, the **whole message** is one stop word, at most 8 characters, or the same stop word repeated (longer repeats count up to 3 times: "stop stop stop", "hold on hold on"; Markdown and quote wrappers — `**停**`, `` `stop` ``, `> 停`, 「停」 — and zero-width characters are dropped first), and it doesn't mention 继续 / 接着 / continue. List (design §3.6 + the owner-approved 等一下 / 等等 / wait, and on 2026-09-29 停下来 / 暂停 / 打住 / 中止 / hold on): 停 停下 停止 先停 停一下 停停 别做了 别跑了 不要做了 取消 等一下 等等 停下来 暂停 暂停一下 先暂停 暂停一下再说 暂停再说 打住 中止 stop abort cancel halt wait hold on. "暂停一下再说" counts as a stop (the owner's intent), while "等一下我再说" / "等等再说" / "wait for it" / "先别停" still don't. A sentence that starts with one ("停！先别合", "Stop hook 为啥没触发", "等等，还有一个需求") is an ordinary message: the agent decides, and Claude Code / Codex are preempted by it anyway. The adversarial review's false-positive list is in `tests/stop-words.test.ts`. A bare "停止 / 取消 / wait" can also be the answer to the agent's own question ("要停止 X 吗？"); when nothing was running the `⏹` headline says "if this answers your question, treat it as the answer". Further missed phrasings from the round-3 review (停吧, 先停一下, 终止, stop it, please stop, …) are not in the list; extending it is the owner's call.

## Cut records

At the moment of the interrupt the bridge snapshots the event bus (`inflightTools(agent)`: tool_start without tool_done since the last `done`). Codex is the exception: its rollout only yields a tool_use once a command has **finished** (no tool_done, nothing for the running one), so for Codex the cut records no in-flight tool and only the last completed command, and the texts say plainly that the cut command can't be seen. A successful tool_done arriving a few seconds after the cut removes that tool from "cut" (it finished just before the interrupt). A cut stores the tools that were running, the last completed step, the side-effect class, the messages the interrupted turn was handling (everything delivered since the last Stop / cut — in a voice burst the follow-ups that arrived inside the preempt cooldown count too; bridge notices only when nothing else), who interrupted, and earlier unfinished cuts (`chain`, for interrupts during the interjection turn). The watcher polls every ~2 s, so a tool that started just before the interrupt shows up late as an errored tool_done; `lateInflight` adds it to the cut.

States: `open` → `resumed` (the agent started the same tool with the same command again — tracked per chain segment; the cut is `resumed` only when every segment is, and the hint lists only the segments not yet resumed), `stopped` (stop word / button / terminal), `hinted` (resume hint generated), `expired` (30 min). Persisted to `turn-cuts.json`, one per channel.

Side-effect classes (`lib/side-effects.ts`, rule table in the test): `none` (reads), `idempotent` (deploy, build, fetch, non-force push, kickstart), `check_first` (manager create/kill/…, commit, merge, Edit/Write, database MCP `query` / `execute`, anything unknown), `external` (tag, release, force push, remote branch delete, publish, peer send_to_agent, HTTP writes via curl / wget / httpie / gh api, writes through MCP servers like Slack, GitHub, Gmail, any MCP order / payment / refund). Cloud CLIs are an allow-list (`lib/side-effects-cli.ts`): kubectl / helm / terraform / aws / gcloud / az are `none` only for read verbs (get / describe / list / show / plan …) and `external` otherwise; gcloud / az look only at the command path before the first option, skip the top-level group, and the first known verb decides (`jobs run get-prices-job` is a run); `kubectl auth` is read only for `can-i` / `whoami`, `kubectl config` only for `view` / `get-*` / `current-context`. Publish / deploy tools (npm unpublish / dist-tag, `yarn npm publish`, docker image push / `--push`, twine, vercel --prod, fly / wrangler / firebase / cdk / serverless deploy, pulumi up, gh secret / variable / gist / run cancel) and write statements through psql / mysql / redis-cli are `external`. Shell structure and wrappers are peeled first (do / then / `{` / `(`, sudo -u X, nice -n N, stdbuf, caffeinate), and `bash -c`, `xargs` and `watch` classify the command they run; httpie on the right of a pipe reads its body from stdin, so it counts as a write. Database MCP tools are recognised by server name or by a tool name that looks like running a statement (sql / query / cypher / statement / database / d1). `\`-newline continuations are joined first, and commands inside `$( … )`, backticks and `<( … )` are classified on their own. Unknown Bash is always `check_first`. Known gaps: Claudestra's own MCP tools (`send_to_agent`, `reply`) are hidden from the watcher for Claude Code / Codex, so a cut during a peer `send_to_agent` shows as "thinking / typing" (the external rule only fires on Pi, whose tool names are bare); per-project external keywords (`extraExternal`) have no config field yet and aren't passed in.

## What the agent sees

1. **Headline** on the interrupting message (`withInterruptNote`, inserted after the source header; the bridge also sets the channel attribute `interrupt_note="true"`, and history parsing — `lib/inbound-body.ts` — strips the note only when that attribute is present, so a user who types the same opening can't hide text from the history; Pi records carry no attributes and keep the note): what was running and whether it can be rerun, what the turn was handling, and that Claude Code's "STOP … wait for the user" tool result is the interrupt's fixed wording, not a request to give up. Stop words get a `⏹` headline instead: stop, confirm, don't resume. An owner stop — stop word from any front end, or the owner's stop button — also clears the channel's inter-agent pendings (watchdog, return slots, in-flight peer calls) like any Discord message does, and does it **before** the keys go out (`setStopHooks` in `bridge/preempt.ts`): Pi reports Stop within milliseconds of the abort, and clearing after the interrupt returned let the watchdog nudge restart it (adv5). One consequence is deliberate (PM's decision): after an owner stop, replies to `send_to_agent` calls this agent made earlier are no longer pushed back to it — a pushback would start a turn on the agent that was just stopped; if the answer is still needed, the owner has it ask again. Headlines quote other senders (guests, peers, agents), so `withInterruptNote` runs them through the delegate-marker neutraliser (`lib/delegate-marker.ts`) before splicing them into the owner's message.
2. **Resume hint** (`[⏯ 打断收尾]`): on the first normal `Stop` after the interrupting message was delivered, if the cut is still open. It goes through the held queue with `waitForIdle`, so it is never sent mid-turn. `Envelope.meta.waitForIdle` has fixed semantics that other features reuse (T11a answers): deliver only when the main turn is idle; while busy or compacting, hold and flush on Stop / compaction end / the minute sweep; never preempt — such an envelope is never an `isHumanRequest`, even from a human. It lists the cut tool with its class and check hint, the last completed step, and the human message the interrupted turn was handling: "not replied" if nothing went to that address since it was delivered, "check whether you answered it" if the only replies came after the cut (they may have answered the interjection). A held hint is dropped before delivery if the agent resumed meanwhile, was interrupted or stopped again (the newer cut chains the unfinished segment), or 30 minutes passed. The Stop of the turn it starts doesn't @ the owner (like Autopilot's nudges). `external` adds a fixed "check first, don't just rerun"; Codex adds "the command may still be running in the background". Never replays anything.

## Runtimes

| | Claude Code | Codex | Pi |
|---|---|---|---|
| Human message while busy | Esc, then deliver (not C-c, below) | Esc, then deliver (typed into the TUI, below) | steered into the running turn, no interrupt |
| Stop word / button | Esc | Esc (only when busy) | extension `abort()` with an `abort_ack` (C-c only clears Pi's editor) |
| Interrupt signal | none (bridge marks done itself) | `Interrupt` hook ~0.5 s after Esc | extension reports `agent_settled` → treated as `Stop` |
| Background subagents | survive (Esc; C-c on an idle main turn would kill them) | — | — |
| Transcript | cut tool_use gets an `is_error` result "The user doesn't want to proceed … STOP …", then `[Request interrupted by user for tool use]` | `<turn_aborted>` developer message; the aborted command **may keep running** (a `ping` finished in the background after Esc, 2026-09-28) | not verified (below) |

### Claude Code: a stuck `thinking` status vs. a clearly idle pane

The event status can stay `thinking` after the turn has ended (interrupted from the terminal: CC sends no Stop; or relit after a Stop). Before, that made the bridge preempt an idle agent, tell it "this message interrupted you, resume what was cut" (it then redid work a human had just stopped) and hold agent messages until the 2-minute reconcile. Now `turnState` (`stuckThinkingIdle`) trusts the pane when it is **clearly** idle: two captures ~1 s apart both idle (prompt present, no spinner, no compaction / API-retry banner, TUI contract recognised) and nothing in the agent's event ring (jsonl activity, deliveries; background-agent progress excluded) for 8 s. The probe then settles the status to `done` (`trigger: pane_idle`). A turn that has just started still counts as busy (the delivery and the first jsonl writes are recent). Codex / Pi keep using the event status only.

### Claude Code: Esc, never C-c (background subagents)

Verified on Claude Code 2.1.283 in the sandbox (2026-09-28), a background subagent running `ping` while the main turn ran a foreground `ping`:

| Key | Main turn busy | Main turn idle, only background agents running |
|---|---|---|
| C-c | main turn interrupted, background agent keeps running | **"All background agents stopped"** — every background agent is killed |
| Esc | main turn interrupted, background agent keeps running | nothing happens, background agent keeps running |

The source agrees: the interrupt handler returns early while a query is running; only when nothing is running does C-c fall through to "stop all background agents", while Esc is bound with `suppressBackgroundAgentKill: true`. Both leave the same transcript markers (the cut tool_use gets the "STOP … wait for the user" error result, then `[Request interrupted by user for tool use]`).

The busy check could say "busy" while the main turn was idle (production on 2026-09-28 22:16:44 preempted an idle PM and killed its background reviewer); with C-c that misjudgment killed background work, with Esc it is a no-op. So Claude Code's `interruptKeys` is `["Escape"]` for preemption, stop words and the stop buttons alike. Graceful exit (`restart` / `kill`) still uses C-c: stopping everything is what exiting means.

Double Esc opens Rewind (≤600 ms apart). Every Esc — interrupts, AUQ cancel, watchers, and manager's `tmux-send-keys` from the Discord buttons — goes through `tmuxSendEscape` (`lib/esc-guard.ts`): the window is identified by tmux's `#{window_id}` (so `master:0` from the interrupt and `windowTarget("master")` from AUQ cancel are the same window; `windowKey` also maps them together as a fallback), sends are queued per window inside a process and a cross-process lock in the runtime dir is held for the whole send (the lock wait, 12 s (`ESC_LOCK_WAIT_MS`), is longer than its 5 s staleness, so a crashed holder's lock is reclaimed rather than skipped; if the lock still can't be had, the Esc is **not sent** — fail-closed: a warning is logged, and the interrupt keys, AUQ cancel (Discord and API), the wedge button, the key panel and manager's `tmux-send-keys` send strictly and report "not sent" instead of success (AUQ state is kept so cancel can be retried); watchers only log; a missed Esc can be pressed again, a Rewind dialog blocks the window), and the next Esc waits until 1200 ms after the previous one **finished** — spacing by scheduled time was not enough: under load a tmux call can take hundreds of ms and two keypresses landed close enough to open Rewind in the sandbox. The gate additionally spaces its own keys ≥1.5 s. An interrupt request can therefore take about 16 s in the worst case (spacing + lock wait + 1.2 s inside the lock), so the bridge's HTTP listeners (main port, legacy web port, peer entrance) raise Bun's 10 s idle timeout to 30 s (`HTTP_IDLE_TIMEOUT_S`) and the web client waits 20 s: a lock that can't be had comes back as "not sent" instead of an empty response. Before sending, a pane in tmux copy-mode is taken out of it (keys would otherwise be eaten by tmux).

Limit: a stop button or stop word no longer stops an agent's background subagents; only its main turn. Stopping those needs Claude Code's own kill-agents chord in the terminal.

### Codex: the queue stalls after an interrupt

Verified on codex-cli 0.153.4 (2026-09-28): after Esc the TUI shows "Conversation interrupted - tell the model what to do differently" and stops taking items from its queue. A message sent with `codex queue` afterwards stays in `~/.codex/queue_1.sqlite` indefinitely; another queue write or an empty Enter does not release it; only a turn submitted from the TUI itself does, after which the queued items run in order. Upstream reports of the same family: [openai/codex#17095](https://github.com/openai/codex/issues/17095), [openai/codex#37974](https://github.com/openai/codex/issues/37974). This also affected the stop button before preemption existed: after it, every later message to that Codex agent stalled.

Fix: the bridge remembers per Codex channel that an interrupt happened since the last normal `Stop` (`TurnCuts.takeAfterInterrupt`, in memory) and tags the next inbound with `meta.after_interrupt`. Codex's `CodexQueueSink` then types that one message into the TUI instead of queueing it (`lib/codex-tui-submit.ts`). Guards around it:

- the channel-server declares `typeIn: true` in its register frame; the bridge only preempts (or sends a stop word's Esc to) Codex channels that declared it — an older channel-server would leave every message stuck in the paused queue while the sender sees "delivered";
- one bridge preempt per Codex turn: until the next normal `Stop`, later human messages queue behind the earlier ones instead of being typed ahead of them (order A, B, C stays A, B, C); stop words still interrupt. Messages already sitting in codex queue can't be pulled back, so a stop word's `⏹` headline lists the ones queued since the last Stop ("sent before the stop — don't act on them when they arrive");
- only a real interrupt pauses the queue: a stop word that sent no key (Codex idle, or blocked) leaves the next message on `codex queue`; the "queued before the stop" list only counts messages queued while Codex was busy;
- if typing can't be done, the channel-server falls back to `codex queue`, posts a notice in the agent's channel that the message waits behind the paused queue, and reports `codex_typein_failed` so the bridge tags the next message again; "pasted but no submit seen" gets a notice too. Both go out as bridge `notify`, not `reply` — the message *is* queued, and a reply would count as the agent's answer (settling the reply ledger, handing a waiting API caller the warning as the result);

- target is the exact pane id from `TMUX_PANE`, and `TMUX` must point at Claudestra's tmux socket; otherwise it falls back;
- it pastes only when the composer is recognisably empty — no busy status line, no dialog or backtrack overlay, and the bold `›` line holds nothing but the dim placeholder (read from `capture-pane -e`); anything else falls back to `codex queue` with a log line, never a blind paste;
- control characters are stripped first (`sanitizeForPaste`: all C0/C1 except `\n` / `\t`, `\r` → `\n`): tmux doesn't remove an embedded `ESC[201~`, and everything after that end-of-paste marker would arrive as keystrokes (`!shell`, C-c) — found by the adversarial review;
- bracketed paste (`set-buffer` + `paste-buffer -p`), so newlines, quotes, `$`, backticks and CJK arrive verbatim (verified live), then Enter; success = the turn starts or the composer empties; a second Enter covers an Enter taken as a newline; if the paste can't be confirmed the composer is cleared before falling back, so a message is never both typed and queued.

Once that typed turn ends, the queue drains normally again (verified: a queued message ran 10 s after the typed turn's Stop). **Takes effect only for Codex agents started after this change** (the channel-server process is per session); running Codex agents need a restart.

### Pi

Pi's C-c only clears the editor (`handleCtrlC` → `clearEditor`; a second one within 500 ms exits), so it never aborted a turn — the adversarial Workflow review confirmed it on Pi 0.85.1 with a fake model. The bridge therefore stops Pi through the Claudestra extension: `PI_CONTROL.abortVia = "extension"`; the extension declares `abort: true` in its register frame only when its session context has an `abort()` (an older extension, or a Pi without it, gets the stop reported as failed instead of "interrupted"); the gate sends `{type:"abort", id}` over the ws — for a stop it skips the bridge's busy check on these runtimes (Pi and ACP Codex: the event state is wrong after a stop, a bridge restart or a turn started in the terminal; the runtime itself answers `idle`); the extension calls the context's `abort()` (the one it saw on `agent_start`) if the agent isn't idle and answers `{type:"abort_ack", id, result: "aborted" | "idle" | "unsupported" | "error"}` — `unsupported` (no `abort()`) and `error` (it threw, e.g. a stale context) are reported as "couldn't interrupt", never as "wasn't running". The stop headline says "interrupted" with an ack, "requested, no receipt" after 1.5 s without one. The Stop Pi reports right after the abort is not a finished turn: it keeps the turn's delivered messages for the stop headline ("sent before the stop, don't act on it"), gives no resume hint and no completion @. Ordinary human messages keep being steered into the running turn (no preemption, no cuts, no resume hints).

Messages steered in before the stop are **voided and echoed back** (PM's decision): the extension (`src/pi/abort-control.ts`) tracks bridge messages steered into the running turn until Pi injects them (`message_start`); on `abort` the ones still queued are voided and listed in the ack (`voided`: message ids), and `bridge/pi-abort.ts` tells their senders "sent before the stop, not executed, voided — resend if still wanted" — each to its own reply address, as a `response` to that message (so it no longer counts as unreplied): a Discord user in the channel they wrote from (+ web); API / web / peer senders at their `api:` address, i.e. the same path as an agent reply (a waiting peer request gets it, `mirror=false` tokens aren't mirrored to Discord; an echo claims only the API request it answers — `takeApiPending` matches `inReplyTo`, so a token with several open requests doesn't get the notice on another one); agents back to themselves (not possible while offline — logged). Voided messages are also taken off the books (`dropVoidedPendings`), whether or not the sender could be told: the missing-reply ledger by message id (with its thread), the agent's return slot for that one request, and the inter-agent watchdog when its sender is the voided message's agent and it was set before the stop — otherwise the bridge would later nudge Pi to handle a message the sender was told won't run. An ack later than 1.5 s still echoes (60 s); acks are only accepted from the channel's current connection. In the TUI (how Claudestra runs Pi) Pi's own abort handler moves queued messages back into the editor; the editor is left alone (someone may be typing in the terminal — PM's decision), the ack reports how many voided messages ended up there (`inEditor`), and the `⏹` headline tells the agent "Pi 输入框里退回了 N 条，未执行" (don't act on them, don't submit them for the user). Without that handler (`--mode rpc`) Pi would start a new run with the queued messages right after the abort (`_handlePostAgentRun` → `continue()`); the extension aborts that follow-up run on its `agent_start`. The same holds in the TUI for runs Pi starts on its own after the abort: `ctx.abort()` there doesn't cancel an auto-retry backoff or an auto-compaction, and Pi continues when they end — so from the abort until Pi settles (at most 60 s) every new run is aborted at `agent_start`, and bridge messages arriving meanwhile (usually the stop itself) are not steered (they would be bounced into the editor) but injected as a new turn after settle. The bridge skips both the missing-reply nudge and the inter-agent watchdog on the first Pi Stop after an abort it sent (`stopAfterAbort`): either would inject a reminder and restart the Pi the owner just stopped. That Stop also settles open API requests with the turn's text (or `reply: null`); an owner's stop word sent with a synchronous wait is registered before the abort (`holdStopWait`; the API route marks the request with `waitUntil` before delivering, because its `resolve` is only attached after `deliver` returns and the preemption runs inside `deliver`) and that Stop skips it (`stopWaitIds`, `apiQueueToSettle`), so the stop turn itself answers it; if that turn doesn't come within 30 s — or 1.5 s before the caller's own wait runs out, whichever is first (e.g. Pi stays idle) — it gets a fixed line — "已叫停 <agent>" plus the abort ack's result (`stopWaitReply`) — never `reply: null`. Verified on Pi 0.85.1 with a fake model (2026-09-29; retry cases after the wf2 review: stop button in the backoff → no retry request, nothing executed; stop word in the backoff → held, delivered after settle): RPC mode, old extension — "部署 Y BASH" started a tool call right after the abort; new extension — ack `voided:["m2"]`, no request for it, the next turn is "等等"; TUI — ack `voided:["m2"]`, nothing sent to the model for it (it sits in the editor, reported as `inEditor`). The `⏹` headline also lists what was sent earlier in the interrupted turn. **Takes effect for Pi agents started after this change** (the extension is loaded at Pi start). Not verified: whether an aborted bash keeps running.

## Autopilot

A stop (stop word, stop button, terminal interrupt) is the human taking over: Autopilot (`bridge/mission.ts`) yields with `human_stopped` until the owner says something that is not a stop — through the bridge, or typed into the Claude Code terminal (`transcriptUserEvent`: a real user text entry in the jsonl, not a slash command, channel injection, background notification, auto-continuation or compact continuation; Pi / Codex transcripts can't tell terminal input from bridge deliveries, so only Claude Code) — no time limit. The stop is kept per channel apart from the latest cut (`turn-cuts-stops.json`: `at`, and `goAt` once released) so a later non-owner preempt that overwrites the cut can't release it; only owner stop-class cuts set it and only the owner's non-stop words clear it; a released entry is dropped 24 h after release (the held-message limit, so `stoppedAt` is still there for anything held before the stop), and `/agent/cleanup` (permanent kill) drops the channel's cut and stop entries (`TurnCuts.forget`) so a new agent reusing the channel doesn't start out "stopped"; text typed into the TUI by cron or `manager tmux-send-keys` isn't the owner (`lib/program-input.ts`: same text within 30 min, or any program key within 5 s) — and with `cut_notice` while a resume hint is still waiting to be delivered, so the hint and Autopilot's "keep going" nudge don't stack.
The owner answering an ask card (web, chat, Discord) also counts as speaking (unless the answer is a stop word); a message an agent forwards (`forward_to_agent`, `meta.forwarded`) does not — when and to whom is the agent's choice — and a forwarded stop word is an ordinary preempt, not the owner's stop. Speaking is compared by time, not arrival order: a stop recorded late (a terminal Esc waits for the program-key check, a stop word for the settle beat) is released at once if the owner already spoke after it, and terminal input read late that predates the stop doesn't release it. The deadline wrap-up ("write the ledger, send a summary") is not delivered while stopped — the run log gets one line instead.

## Sandbox results (2026-09-28, Claude Code)

Long foreground command cut by an interjection → headline delivered → agent answered, inspected the half-written file and reran it on its own (cut `resumed`, no hint). Interjection that asked for an answer only → `Stop` → resume hint 2 s later listing the cut command and the unreplied request → agent checked and reran. `停。` → interrupt (then C-c; Esc since the switch) → `⏹` headline → agent confirmed stop, no hint. API stop → `manual` cut, stopped.

## Held messages across a stop

Owner answers to asks (`waitForIdle`) and agent requests are held while the target is busy and flushed after its Stop — i.e. after a stop that came later. `flushHeld` puts a headline on anything held before the channel's last stop (`heldAcrossStopNote`: "sent before the stop, delivered only now — don't act on it, ask the user"), stripped from history like the other headlines. When the target is killed while an owner answer is still held, the ask goes back to open (`reopenAsk`, event `ask_reopen`, answer cleared) and the owner is told in #control to answer again (it then goes to whoever `answerTarget` finds at that time).
