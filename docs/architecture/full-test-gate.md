# Full test gate (本机全量测试闸)

Every executor on one machine runs `bun run check` before each commit, and `check` runs the whole `bun test` suite. Five full runs at once saturate the machine (load, swap) and turn timing-sensitive tests red that pass when run alone. The gate caps how many **full** `bun test` runs execute on this host at the same time (owner decision: at most 2). Runs with test files / paths are never gated.

The admission logic is the existing `src/lib/lend-check-permit.ts` (SQLite-serialized queue, process identity, approval check, tree-confirmed reclaim). This feature only wires it in; it does not change how the permit decides.

`package.json`: `test` = `bun scripts/test.ts`, `check` = `bun run typecheck && bun run test && bun run guard` (only the test step holds a slot; tsc and guard don't).

## Rules

- **Full run** = no positional argument. Known `bun test` options are parsed with their values (`--timeout 10000`, `-t name`, `--preload ./p.ts` are not files). Options whose value is optional (`--bail`, `--changed`, `--parallel`) only take it as `--x=v`, as bun does. Anything unrecognised exits 2 with "测试未启动" — no guessing. That includes unknown options **before** `test` on a direct `bun …` command line (`bun --console-depth 5 test`): the scan stops there instead of reading the option's value as a script name and calling the run `other` (ungated). Known value options (`bun --cwd . test`) and `--x=v` skip their value; `-e` / `--eval` / `-p` / `--print` / `-` and a script name stay `other`. A run with a file/path is passed straight to `bun test`, no queue, no slot.
- **CI short-circuit**: `CI=true` or `GITHUB_ACTIONS=true` → `scripts/test.ts` spawns `bun test <args>` unchanged and the preload hook returns at once. Neither reads the policy nor opens the permit store, so ci.yml's `--shard=99999/99999` discovery probe and log format are unchanged.
- **Host directory**: `stateDirIn(homedir())/locks/full-tests/` — it deliberately ignores `CLAUDESTRA_STATE_DIR`. The preload, worktrees and sandboxes each point that variable somewhere else; following it would give every process its own 2 slots. Tests always pass an explicit temporary directory (or a temporary `HOME`).
- **Policy** (`policy.json` in that directory): `{mode: off|observe|on, max, maxWaitMin, source}`. Missing / unreadable / invalid → `observe` (the last two with a stderr note). `on` without `source` → `observe` with a stderr note — the gate never claims to limit when the approval is missing. Defaults: `max` 2, `maxWaitMin` 60. Not in `config.json`: config-store's whitelist read/write drops unknown keys. The approval handed to the permit is verified against the same host policy (`approvalVerifier`), never against caller strings.
- **Supervisor** (`scripts/test.ts`) owns the permit and is the only holder of a slot. Spawn order, so that a holder SIGKILLed at any point never leaks a slot or lets a test run unaccounted:
  1. write `trees/<id>.json` = `{state: "spawning"}`;
  2. spawn `/bin/sh -c 'read <&3 || exit 125; exec 3<&-; exec bun test …'` in its own process group — the shell blocks on fd 3 (the **go-gate**);
  3. read the shell's identity (PID = pgid, start time, macOS unique id — `exec` keeps all three) and write `{state: "running", pgid, start, uniq, boot, members: []}` (`boot` = this boot's identity);
  4. write the go line; only now does `bun test` start.
  If the supervisor dies before step 4, its end of the pipe closes, the shell reads EOF and exits without starting the test. So `spawning` means "never started and never will", and the observer reports it `absent` — the permit only reclaims it once the holder itself is confirmed dead.
- **Tree observer** (`full-test-gate-tree.ts`). The supervisor samples the process table every 500 ms (macOS: libproc plus `getsid`, without subprocesses; Linux: `/proc`). It recognises the root, previously sampled members by PID + start time, live parent links, and macOS original-parent version / unique ID links. Each recognised member's pgid and sid, including the isolated test root's keys, are persisted in the tree record as `{id, leaderStart}` — the start time of the group leader / session leader (the process with pid == id) when the key was recorded, `null` if it was already gone; old plain-number arrays are still read. Processes sharing either key are also recognised, even if an intermediate parent disappeared between samples. Sampled descendants remain members after reparenting or changing groups, with no time expiry. Both the holder and later acquirers persist newly discovered members and keys. Other processes' environments are never read.
  Keys expire, so they cannot accumulate unrelated processes over time or across reboots:
  - every scan prunes them: a process with pid == id but a different start time means the number was reused → key dropped; no process has that pgid / sid and no pid == id → the group / session is gone (the kernel won't hand the number out while it is in use) → key dropped. 0 and 1 are never keys; members with a different uid than the root contribute no keys. The record stores the pruned set (no longer grow-only);
  - a process recognised only through a key (pgid / sid / original-parent version / original-parent unique id) must not have started before the root (compared within one boot; start formats that can't be compared keep the old behaviour). Members already tracked by PID + start time are unaffected;
  - boot identity (Linux `/proc/sys/kernel/random/boot_id`; macOS `kern.bootsessionuuid` via `sysctlbyname`, no subprocess — `kern.boottime` shifts when the clock is stepped, so it is used only for the next rule): a record from another boot is `absent`. A legacy record without `boot` is `absent` when its root started before this boot (Linux: the root's start embeds its boot id; macOS: root start < `kern.boottime`). An unreadable boot identity, when needed, is `unknown` (slot retained). After a reboot the old pgids / sids are system processes, which is how a stale record could stay `present` forever.
  **Record writes** (`full-test-gate-record.ts`): the holder's periodic `track` and every observer go through one entry point. Under a per-record lock (`tree-locks/<id>.lock`, same mkdir + owner-token protocol as `src/lib/file-lock.ts`, but synchronous because the permit calls the observer synchronously) it re-reads the latest record and merges three-way (what the caller read, what it computed, what is on disk now): members / keys someone else added since are kept, ones the caller pruned are not revived. A corrupt record is never overwritten (`unknown`, slot kept); a deleted one (already released) is not recreated.
  A descendant that leaves all known groups / sessions and whose intermediate parent lived entirely between samples cannot be attributed reliably. On macOS a same-user reparented process whose original-parent version is no older than the root is **unclaimed**. It is never signalled, since it may belong to another program. Once all recognised members are gone, `quietAt` starts a grace period (`orphanGraceMs`, default 60 s). Unclaimed processes hold the slot only until that grace expires, with stderr stating “有无法归属的进程仍在，按宽限释放”. This is an accepted approximation for host load limiting, not a security boundary. Recognised members and descendants sharing known pgid / sid keys never expire this way. Linux lacks original-parent versions; its unclaimed fallback uses same-user processes born no earlier than the root and reparented to PID 1. Reparenting to another subreaper outside the known keys remains a blind spot. An unreadable process table means `unknown`, retaining the slot.
- **Release**: after `bun test` exits the supervisor waits up to 10 s for the whole tree (escaped descendants included) to be gone, then releases. If something is still there it does **not** release; the slot is reclaimed by the next acquirer once the permit's sweep sees the owner dead and the tree absent. A SIGKILLed supervisor is reclaimed the same way — a missing parent PID alone is never enough.
- **Direct `bun test`**: in the preload `process.argv` is already rewritten to the first test file, so the hook reads the kernel's argv (`/proc/self/cmdline` on Linux, `sysctl KERN_PROCARGS2` on macOS). If it cannot be read, the run is treated as full. A full run without a permit marker is handed to `scripts/test.ts` (the preload cannot be the holder: nobody would be left to confirm that its own tree has exited). The outer `bun test` process just waits for it and returns its exit code. `scripts/test.ts` sets `CLAUDESTRA_FULL_TEST_PERMIT` on the `bun test` it starts (permit id, or `focused` / `unregistered` / …). The preload sees it and does nothing, so there is one slot per run. Nested `bun test` spawned by tests inherit it.
- **Queue**: a stderr line at the first poll and every 30 s after that: mode, max, queue position, time waited, worktree, request id. A line with the wait time on admission. Past `maxWaitMin` the request is cancelled and the run exits 75 with "测试未启动" — `bun test` is never started, and the result is never reported as a pass or a test failure. A gate refusal (store / identity failure after retries, unverified approval) is the same 75.
- **Signals**: while queued, SIGINT / SIGTERM / SIGHUP cancel the request (exit 128+n, "测试未启动"). While running, they are forwarded to the whole `bun test` group (it is not in the terminal's foreground group) and to every escaped tree member found by a fresh scan; the supervisor then waits for the tree and returns the test's own exit code.
- **observe**: never blocks. Each full run is still registered (permit entry + `runs.jsonl`: who, when, worktree, how many were running, which queue position it would have under `on`, wait, duration, exit code). When it would have queued, one stderr line says so.
- **Mode changes**: the approval reference carries `source` only in `on`; `observe` always uses the store's observe default, and `set observe` / `set off` drop the old `source` unless `--source` is given explicitly — otherwise a leftover `source` from an earlier `on` makes every full run hit `policy_conflict` while any attempt is registered. Per the permit, a different policy can only be installed when no attempt is registered. A run that sees `policy_conflict` keeps polling until the old attempts drain. A queued run keeps the policy it queued under (its own cancel must match). An idle `on` store refuses to go back to `observe` (the permit's no-downgrade rule). Observe runs then go unregistered with a stderr note. `off` always bypasses.

## Owner workflow

`bun run test:gate status` shows the effective policy, registered attempts and a summary of `runs.jsonl` (peak concurrent full runs, how many would have queued at `max`, longest real wait). After the observation period: `bun run test:gate set on --max 2 --source <approval ref>`. `set on` refuses without `--source`. Peers upgrade into `observe` (no policy file) and choose for themselves.

`bun run test:gate sweep` lists every registered attempt with its holder state and tree verdict (`absent` / `present` / `unknown` and why); it writes nothing. `sweep --apply` reclaims through the permit's own dead-holder sweep: it makes one acquire under the policy currently stored in the permit store (so it never switches mode and cannot be rolled back by `policy_conflict`), immediately releases / cancels that acquire, and appends a `sweep` line to `runs.jsonl`. Only attempts whose holder is gone and whose tree is `absent` are reclaimed; `present` / `unknown` stay. It never edits or deletes the store. Once ownership is fixed, ordinary acquires reclaim such leftovers too — `sweep` is the visible, on-demand entry point.
