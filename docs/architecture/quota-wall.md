# Usage-limit wall (额度闸)

Every Claude Code agent on one machine runs on the same subscription. When one of them hits the weekly or 5-hour limit, all of them have — the next turn anywhere fails with the same synthetic `You've hit your weekly limit · resets …` entry. Before the wall existed (2026-09-28 22:19), that turned into a mess: the 60-second API-error auto-resume woke 11 agents that failed again at once, every agent→agent message woke a turn that failed immediately, the Stop-hook drain fallback forwarded the limit text to callers as if it were their answer (and consumed the return route), and after the owner used a reset card someone had to press Esc in 12 windows and re-nudge every agent by hand.

The wall makes that one machine-wide state handled by the bridge.

## Rules

- **Enter** on an `api_error_turn` whose `error` is `rate_limit` **and** whose text starts with `You've hit your … limit` for an account window (weekly / session / usage / plain "limit") — `wallHitOf` in `lib/quota-wall-text.ts`, shared with the drain fallback. A single model's limit ("You've reached your Fable limit") is shown as ⛔ but doesn't gate the machine; "Server is temporarily limiting requests" and 429 "would exceed your account's rate limit" keep the normal 60-second resume. The limit text is only matched on the synthetic error entry, never on agent prose. Reset text may carry a year across New Year (`Jan 2, 2027 at 6am`). Or when the status-line cache shows ≥ 100 % (values above 100 are clamped to 100, as the probe DTO does) for a window whose reset time hasn't passed; after a wall that didn't end on its reset time the cache can re-open one only once that window's reset time moved later than the old wall's (cache or reset text). Later hits merge (kind = the heavier one, reset time = the later one). Only Claude Code agents (master included).
- **While walled**, `deliverToLocal` holds every message to a gated Claude Code agent that isn't from a human (agent→agent, peer, bridge-synthesised). A window whose footer says `Lower priority until …` (low-priority on, actually running) isn't gated: messages go through and Autopilot doesn't yield. Human messages go through unless the window sits on the limit menu / countdown (next rule). Wall items never age. The ageing sweep and the return-book sweep pause only for Claude Code senders / targets (Codex and Pi age normally); Autopilot's `wallUntil` and the exit release apply only to Claude Code missions. Auto `/save-compact` (emergency line included) skips only windows currently on the menu / countdown. A return slot marked `apiErrorAt` that expires (2 h) or whose target is killed tells the caller with the fixed template plus the withheld text (`onExpired`), never silently.
- **No key on the limit menu or the countdown** (`paneShowsWallWait` / `wallWaitKind`), walled or not. Both preempt entries (Discord inbound and `deliverToLocal`) go through `interruptGate`, which asks the screen first and again 300 ms before sending the key (and re-probes that the turn is still running); `deliverToLocal` then holds the message (`heldBy: "wall_menu"`, or `quota_wall` for wall holds) — also when the gate's 300 ms re-check is what saw the screen (`preemptForHuman` returns `wall_wait`). An owner's 停 held there is recorded on the spot (stop cut, agent pendings cleared, Autopilot yields); as soon as the window shows activity again (Claude Code continuing on its own) the held human messages are flushed, so the 停 lands within seconds instead of at the next minute sweep. `send_to_agent` and the messages API (202, no waiting) report it; the API only reveals `heldBy` to full-scope owner credentials (`canSeeQuota`), others get `queued: true` (the web treats both as held; the slash 409 text is neutral for them too). A human in a Discord channel gets one notice per new message, plus one per channel when the screen state (menu / countdown × walled) changes — not per retry. The web marks the bubble as held (kept past the 30-minute optimistic window, with its own "held" mark that survives the system line being dropped on resync) and adds a system line. Cron to an existing agent fails the run instead of typing, and Web / Discord slash passthrough refuse (409 / reply) — `lib/wall-screen.ts`. The launcher's modal auto-confirm never presses Enter on a limit menu. A human message held 24 h and given up is reported back to its sender with the original text: Discord in its channel, Web / API / peer on its `api:<token>` conversation (settling that request's wait); only the owner is told it was the limit menu. The stop button and `manager tmux-send-keys` are T41 debt.
- **API errors while walled** are recorded for resume-on-exit instead of the 60-second resume, and never escalate. A single model's limit isn't auto-resumed either — the channel gets one message saying to switch models with `/model`.
- **Drain fallback** (`bridge/stop-settle.ts`): a turn that ended in an API error doesn't settle the send_to_agent return route; non-wall errors push one notification per slot; API waiters resolve with `{reply: null, apiError: true}`. Every waiting slot gets `apiErrorAt`. What the agent said before the error is withheld **only on the slot it belongs to**: the single agent whose request opened the turn; several callers, or a turn no agent opened (owner / bridge) → nothing is withheld and the owner gets one #control line saying which case and how many callers wait (never A's words to B; silent while walled). What settles the slot depends on who opened the turn (`noteDelivered`, at the actual send): the first message, raised to the strictest source (stranger > owner > insider) by anything within 3 s, never lowered; a message reaching an idle target more than 3 s after the record starts a new record (interrupted turns have no Stop); a turn with no record (Claude Code continuing on its own at the reset time, the owner typing at the terminal) and a turn opened by the bridge's resume messages inherit the record of the last turn that ended in an API error (else the previous turn) — a stranger's turn in between doesn't change it; unknown after a restart = stranger. Insiders and the owner settle; guests, scoped / external tokens and peers don't (their turn re-arms a cancelled 60-second resume). Withheld text goes to its caller as its own message headed「撞墙前扣下的答复」, per slot, also when the slot is consumed directly (`onWithheld`), to `originalReplyChannel`. A push counts as failed on a thrown error **or** an `error` / `dropped` outcome; then the settling turn's text is withheld on its own slot. A failed `send_to_agent` delivery only drops that one request (`dropRequest` is not an answer).
- **Notify** the owner once, 20 s after entering: kind, reset time, queued agent messages, how many resets are held (`held`, not `applicableNow`: a default card only becomes usable after hitting the limit), human messages held at menus / countdowns, that direct messages go through except to windows on the menu / countdown, that a reset used elsewhere needs "It's back" / `quota-wall clear`, and whether the read-only probe is unavailable (also on the banner). The banner shows the held resets too. The bridge never uses a card and never picks a menu option.
- **Exit** on the first of: reset time + 1 min (fallback: the cache's reset time, else 5 h / 7 days); a new `Limits reset · …` echo — only the `⎿` line right under a column-0 `❯ /limit-reset`, compared by content against a baseline taken with 2 000 lines of history at entry (after a bridge restart inside the wall the baseline is re-taken the same way and that tick doesn't judge) (quoted echoes and old echoes revealed by a taller window don't count); the read-only probe (every 5 min) showing < 100 %; the status-line cache, per window: a weekly wall only when the 7-day reset time moved later and 7 d < 100 (a writer that only knows `five_hour` may rewrite 7 d downwards); a session wall likewise only when the 5-hour reset moved later and 5 h < 100 (a stale writer can write back the previous window's low value); a window that reads null is unknown, a 5 h roll-over never opens a weekly wall, and a probe newer than the cache sample saying ≥ 100 vetoes it; `quota-wall clear` / the banner button.
- **Recover** in persisted, idempotent steps, each checking the wall id is unchanged: (1) capture; only a window whose screen is *exactly* the limit menu is taken out of copy-mode, captured again 300 ms later and sent one Esc; anything else is listed for the owner; a menu still there afterwards is listed as not closed; (2) wall items back to normal held items, flushed in order; (3) `[额度恢复] …` to each interrupted agent that isn't running and whose flush didn't deliver an insider / owner message (a flush of only guest / peer messages still gets the resume, queued behind that turn). A window only waiting on the wall isn't "running" (`wallWaitKind`: a limit menu — title + hint + any limit option, joined across Ink's wrapped lines and promo lines — or `Usage limit reached` / `continuing automatically at` / `/low-priority to continue now` in the footer under the input box, including the truncated weekly, "when it resets" and "continuing shortly" forms. The input box is recognised by shape, not by what follows ❯: a column-0 rule of only `─`, directly under it a column-0 `❯` (or `!` in shell mode), only indented or blank lines until the next such rule, and no column-0 text below it (a draft starting with "1." is still the box; permission / AskUserQuestion / limit menus aren't). Only a column-0 spinner row in the spinner zone counts as still running, since a busy screen pasted into the transcript is indented and a column-0 prompt line saying "esc to interrupt" isn't a spinner; samples in `tests/fixtures/quota-wall/`). A resume that comes back held (window still on Claude Code's countdown / menu) or not delivered isn't counted; held ones are listed in the exit notice for the owner. Only real jsonl activity or an outgoing message (`countsAsWallActivity`) takes an agent off the resume list.
- **Web**: API-error entries render as one system row, consecutive identical ones merged as `×N`, the same in history, live and delta sync (a delta's recomputed `×N` row replaces the tail row).

## Integration points

- `quotaWall()` (from `bridge/quota-wall-wiring.ts`) exposes `active()`, `gates(channelId)`, `until()` (reset time while walled) and `onExit(cb)`; `onQuotaWallExit(cb)` works before the wall is created.
- Autopilot: `yieldReason` yields with `quota_wall` while the agent is gated (the nudge would only be held); a `rate_limited` run's next wake uses `until()` over its own text (`RunEvidence.wallUntil`, set in `autopilot-close.ts`); on exit every `hold: "rate_limit"` wake is released at once (`releaseRateLimitHold`). Its "compact first" and deadline nudges are ordinary bridge messages, so they are covered by the same yield and, failing that, by the hold.
- Reset-time parsing has one implementation: `lib/usage-window.ts#parseResetText` (time zone, year roll-over, DST, weekday-only `Fri 9am`, time-only). `autopilot-run.ts#parseResetAt` only locates the reset phrase (CC `resets …`, Codex `try again at/in …`) and applies the 8-day plausibility window.
- The recovery resume message should move to `meta.waitForIdle` once that exists; until then the bridge checks the main turn is idle right before sending.
