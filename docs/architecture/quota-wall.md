# Usage-limit wall (额度闸)

Every Claude Code agent on one machine runs on the same subscription. When one of them hits the weekly or 5-hour limit, all of them have — the next turn anywhere fails with the same synthetic `You've hit your weekly limit · resets …` entry. Before the wall existed (2026-09-28 22:19), that turned into a mess: the 60-second API-error auto-resume woke 11 agents that failed again at once, every agent→agent message woke a turn that failed immediately, the Stop-hook drain fallback forwarded the limit text to callers as if it were their answer (and consumed the return route), and after the owner used a reset card someone had to press Esc in 12 windows and re-nudge every agent by hand.

The wall makes that one machine-wide state handled by the bridge.

State: `~/.claude-orchestrator/quota-wall.json` (written on every change, survives bridge restarts). `manager quota-wall clear` drops `quota-wall-clear.req` next to it; the bridge picks it up on its next 15 s tick (no HTTP route: the CLI has no `/api/v1` credential, and the request survives a bridge that is down).

## Rules

- **Enter** on an `api_error_turn` whose `error` is `rate_limit` **and** whose text starts with `You've hit your … limit` for an account window (weekly / session / usage / plain "limit") — `wallHitOf` in `lib/quota-wall-text.ts`, shared with the drain fallback. A single model's limit ("You've reached your Fable limit") is shown as ⛔ but doesn't gate the machine; "Server is temporarily limiting requests" and 429 "would exceed your account's rate limit" are transient throttles that keep the normal 60-second resume. The limit text is only matched on the synthetic error entry (CC `isApiErrorMessage`, Codex's translated entry with `error`), never on agent prose, and `limit` must be followed by punctuation or end of line. Or when the status-line usage cache shows ≥ 100 % for a window whose reset time hasn't passed. After a wall that didn't end on its reset time (card / clear / probe), the cache can't re-open a wall for the same window: using a card keeps the weekly reset day, and the next render writes the old 100 % back with a fresh `scrapedAt`. Later hits merge into the same wall (kind = the heavier one, reset time = the later one). Only Claude Code agents (master included); Codex and Pi have their own quotas.
- **While walled**, `deliverToLocal` holds every message to a Claude Code agent that isn't from a human (also when the target is mid-turn — those get `reason: "quota_wall"` too; anything held by other paths, e.g. a push-back to an offline caller or an ask reply, is re-marked on the next flush of a walled channel) (agent→agent, peer, bridge-synthesised: missions, api-error-resume, watchdog nudges). Human messages (Discord user, non-peer API user, button clicks) go through — the owner may be on their way to `/limit-reset` in that window. Held wall items never age (no "still queued" notice, no 24 h give-up), and the whole ageing sweep pauses while the wall is open (its notice is a raw `ws.send` to the sender, which would wake a turn that hits the wall). The automatic `/save-compact` of the stats dashboard doesn't fire while walled. The send_to_agent return book isn't swept while walled and its clocks restart on exit.
- **API errors while walled** are recorded for resume-on-exit instead of the 60-second resume, and never escalate. A single model's limit (outside the wall) isn't auto-resumed either — the channel gets one message saying to switch models with `/model`, and the caller's notice says the same.
- **Drain fallback** (`bridge/stop-settle.ts`): a turn that ended in an API error (Claude Code's `StopFailure`, or last assistant entry `isApiErrorMessage`) doesn't settle the send_to_agent return route — the error text is never captured as an answer, pending kept, and whatever the agent said before the error is withheld and sent with its eventual answer. Errors that aren't the wall push one `intent: notification` to each waiting caller per slot (`[ℹ️ X 这轮以 API 错误结束：…；回程保留…]`). API waiters are resolved in that same turn with `{reply: null, viaFallback: true, apiError: true, error}` — leaving them open would let an unrelated later turn answer them. Codex's `StopFailure` (synthesised for its quota errors, mapped from its Interrupt) settles as before. After such a turn every waiting slot is marked `apiErrorAt` (persisted with the return book, so it survives a restart and covers several callers) and what settles it depends on who triggered the turn, recorded by `noteDelivered` when the message is actually sent (not `lastMessageSource`, which the API route overwrites): the bridge / another agent (resume, flush, auto-resume) and the owner (Discord, the owner's web devices / web-ui, `owner:self` API — `isOwnerSource`) settle it, since the owner and the caller are on the same side; guests, scoped or external tokens and peers don't, and what the agent said to them is not withheld. Unknown (after a restart) counts as not the owner. The withheld text goes to the caller as its own message headed「撞墙前扣下的答复」, before and separate from the settling turn's answer. A Discord message in that channel doesn't count as a takeover (the route isn't cleared).
- **Notify** the owner once, 20 s after entering (so the first wave is merged in): kind, reset time, how many agent messages are queued, how many reset cards are usable (read-only from T2b-2's data). The bridge never uses a card and never picks a menu option.
- **Exit** on the first of: reset time + 1 min (no reset time in the text → the reset time seen in the usage cache during the wall, else 5 h for session / unknown and 7 days for weekly); a new `Limits reset · …` echo in any Claude Code window (echoes already on screen when the wall started don't count); the T2b-2 read-only usage probe, every 5 min, showing < 100 % (its own interval, backoff and `quotaClaudeBackground` switch apply); the status-line cache showing < 100 % after it showed ≥ 100 % during this wall, or with a different reset time than first seen (the cache only ever rises within a window, so "scraped after entry" alone proves nothing); `quota-wall clear` / the web banner's button.
- **Recover** in persisted, idempotent steps, each checking the wall id is unchanged (hitting the wall again mid-recovery starts a new wall; the old recovery stops and its un-resumed agents carry over): (1) take the pane out of copy-mode, then send one Esc to every window whose screen is *exactly* the limit menu — title, consecutive options starting with "Stop and wait for limit to reset", every option a known label (from the Claude Code binary), the Esc hint as the last line; anything else is logged and listed for the owner, never keyed; the screen is captured again afterwards and a menu that is still there is listed as not closed (no retry); (2) turn wall items back into normal held items (fresh timestamps) and flush channels in order of their earliest item; (3) send `[额度恢复] …` to each interrupted agent whose queued messages weren't actually delivered by step 2 and that isn't already running. "Running" excludes a window that is only waiting on the wall (`paneShowsWallWait`: the menu, or the `continuing automatically at … · esc to cancel` countdown — both trip the generic busy regex); likewise only real jsonl activity or an outgoing message (`countsAsWallActivity`) takes an agent off the resume list, not a message being delivered to it. Then one notice: menus closed, messages delivered, agents resumed, duration.
- **Web**: API-error entries render as one system row, consecutive identical ones merged as `×N`, in history and live.

## Integration points

- `quotaWall()` (from `bridge/quota-wall-wiring.ts`) exposes `active()`, `gates(channelId)`, `until()` (reset time while walled) and `onExit(cb)`; `onQuotaWallExit(cb)` works before the wall is created.
- Autopilot: `yieldReason` yields with `quota_wall` while the agent is gated (the nudge would only be held); a `rate_limited` run's next wake uses `until()` over its own text (`RunEvidence.wallUntil`, set in `autopilot-close.ts`); on exit every `hold: "rate_limit"` wake is released at once (`releaseRateLimitHold`). Its "compact first" and deadline nudges are ordinary bridge messages, so they are covered by the same yield and, failing that, by the hold.
- Reset-time parsing has one implementation: `lib/usage-window.ts#parseResetText` (time zone, year roll-over, DST, weekday-only `Fri 9am`, time-only). `autopilot-run.ts#parseResetAt` only locates the reset phrase (CC `resets …`, Codex `try again at/in …`) and applies the 8-day plausibility window.
- The recovery resume message should move to `meta.waitForIdle` once that exists; until then the bridge checks the main turn is idle right before sending.
